# ADR-017: 去掉兜底分类，AttachmentCategory 按 project_type 隔离

## Status
Proposed

## Context

当前 `AttachmentCategory` 表中，project 类型的分类使用 `project_type=NULL` 作为"兜底分类"，所有项目类型共享同一套分类。这导致以下问题：

1. **管理混乱**：管理员无法给不同项目类型（数据服务/算力服务/卫星服务）配置不同的附件分类
2. **数据重复**：`init_default_categories` 的幂等判断仅按 `contract_type + code`，在多次部署/操作后可能产生重复的兜底分类记录
3. **删除影响面不可控**：修改/删除一个兜底分类会影响所有项目类型
4. **与 project_type 的设计自相矛盾**：合同有 project_type 字段，但分类却共享

## Decision

**去掉兜底分类概念，每个 project_type 拥有独立的一套 AttachmentCategory。**

具体变更：

1. `AttachmentCategory.project_type` 不再允许 NULL（对于 project 类型），每个 project_type 必须有专属分类
2. `init_default_categories` 不再创建 project 类型的默认分类
3. `_ensure_payment_attachment_items` 接收 `project_type` 参数，创建专属回款凭证分类
4. `list_categories` 去掉空字符串查询 `project_type IS NULL` 的逻辑
5. 前端 `project-attachment-categories.vue` 去掉"兜底分类"标签和交互
6. 前端 `attachment-categories.vue` project tab 下 `project_type` 必填

## Consequences

### 变容易了
- 不同项目类型可独立配置附件分类
- 不会再有重复分类的 bug
- 分类管理操作的影响面精确可控

### 变难了
- 新建 project_type 后需要手动创建对应的附件分类（不再自动"兜底"）
- 需要一次数据迁移，将现有兜底分类分配到对应的 project_type

### 可逆性
- **高**。`project_type` 字段仍存在，如果需要恢复兜底逻辑，只需将 `project_type` 改回 NULL 即可。
- 迁移脚本会保留原始 `project_type=NULL` 的数据备份。

## Migration Plan

迁移策略：**只改 `AttachmentCategory.project_type`，不动任何 ID**。

由于 `Attachment` 和 `AttachmentStatus` 通过 `item_id` 间接关联 `AttachmentCategory`，只要 `category.id` 和 `item.id` 不变，已有数据完全不受影响。

### 步骤

1. 查询所有 `contract_type='project'` 且 `project_type IS NULL` 的 AttachmentCategory
2. 对每一组同 code 的分类，按 `contract_id` 反查合同的 `project_type`
3. 将有合同引用的分类的 `project_type` 更新为对应值
4. 删除（软删除）无合同引用的重复分类
5. 为每个 project_type 补充缺失的分类（如果某类型下没有完整的一套分类）
